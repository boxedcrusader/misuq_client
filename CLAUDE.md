# Misuq — Frontend (client/)

Scope note: this file covers `client/` only (web + mobile). The backend lives in `../service` and is owned separately — do not edit it from here. The backend's own project brief is `../README.md` / `../CLAUDE.md`.

**Maintenance rule: update this file after every task completed in `client/`** — add what changed, don't just leave it stale. Keep entries short; link to files instead of pasting code.

## What this is

Marketing landing page for Misuq (AI marketing copilot for indie SaaS founders), built twice:
- `client/web` — Next.js 16 (App Router, Turbopack) + Tailwind v4, for desktop/browser.
- `client/mobile` — Expo (React Native + TypeScript), for the native mobile view.

Both are independent projects (not a monorepo/workspace) that each carry their own copy of the same design tokens. This was a deliberate choice over a shared `packages/tokens` workspace — keep it that way unless asked to change it.

## Design source of truth

`client/design_handoff_misuq_landing/` — do not edit these files, they're the reference:
- `README.md` — full design token table (colors, type scale, radii, shadows, layout, copy) and section-by-section spec. This is the primary spec to check against, more reliable to read than the `.dc.html` files.
- `Misuq Landing.dc.html` — reference markup/inline-styles for the landing page (ignore the `<x-dc>`/`support.js` authoring runtime, only markup+styles+copy matter).
- `Misuq Design System.dc.html`, `Misuq Logo.dc.html` — supporting references, already folded into the README's token table.

Each app keeps its own token mirror:
- `client/web/src/lib/tokens.ts` + `client/web/src/app/globals.css` (`@theme` block — Tailwind utility colors like `bg-indigo`, `text-deep-ink`, etc.)
- `client/mobile/src/lib/tokens.ts` (`colors`, `fonts`, `radii`, `spacing` consts used directly in `StyleSheet.create`)

If the design handoff changes, update both token files by hand — there's no codegen link between them.

## Structure

```
client/web/src/
  app/               layout.tsx (fonts, metadata), page.tsx (composes sections), globals.css (tokens)
  components/        Nav, Hero, Problem, HowItWorks, ReportBack, Pricing, ClosingCta, Footer, Logo
  lib/tokens.ts

client/mobile/
  App.tsx            loads fonts (expo-font + @expo-google-fonts/*), renders LandingScreen
  src/screens/LandingScreen.tsx   composes sections inside a ScrollView
  src/components/    Nav, Hero, Problem, HowItWorks, ReportBack, Pricing, ClosingCta, Footer, Logo, Button, ChatBubble
  src/lib/tokens.ts
```

Section components are 1:1 with the design handoff's "Screens / Views" list (nav, hero, problem statement, 5-step how-it-works, report-back chat demo, 3-tier pricing, closing CTA, footer). Mobile collapses the 5-col and 3-col grids to single-column stacks (no responsive breakpoints needed since it's always phone-width); web collapses via Tailwind `sm:`/`md:` breakpoints.

## Backend integration screens (`client/web` only — not built on mobile)

Separate from the static landing page above: real screens wired to `../service`'s live NestJS API, one per V1 loop step (README §2). Each follows the same discipline — typed client in `src/lib/api.ts` mirrors the real backend DTOs/response shapes verbatim (verified live, not assumed), one screen per slice, status is always read back from the server (`getStory`) rather than computed client-side, real guard errors (409/400) surfaced as specific messages instead of generic failures. Dev auth stand-in: `x-user-id` header, seeded id hardcoded in `api.ts` (`getDevUserId`); seeded audiences in `DEV_AUDIENCES`.

- [x] `/capture` (`CaptureFlow.tsx`) + `/send` (`SendFlow.tsx`) — capture → draft, and stage a drafted piece to a seeded audience. See commit `d63f7ec` for full detail.
- [x] `/report-back` (`ReportBackFlow.tsx`, 2026-08-09) — STAGED → REPORTED. Sources reportable Sends via `listSends` (`GET /sends`, bare rows) enriched per-row with `getSend` (`GET /sends/:id`, includes `contentPiece.story`) — there is no list endpoint that returns the enriched shape directly, so the picker does the join client-side. One freeform `<textarea>` → `reportBack` (`POST /reports`); response has no `Story.status` (same gap as `draftStory`/`stagePiece`), so `getStory` is called afterward for the authoritative status. Deliberately does NOT render the created `SignalRecord` (views/replies/sentiment/etc — stub-extractor output) since judging extraction quality isn't this screen's job. Niche-missing 400 and duplicate-report 409 (`ConflictException`, "already been reported on") both surfaced as specific messages via `describeReportError`, reusing `ErrorBanner` (now takes an optional `message` override prop so callers can pass a transformed string instead of `error.message` verbatim). Verified live: full round-trip (STAGED → submit → REPORTED) and the duplicate-guard 409 both exercised in-browser against the running backend, no console errors.
- [x] `/graduate` (`GraduateFlow.tsx`, 2026-08-10) — REPORTED → GRADUATED, the final loop slice; completes the clickable loop end-to-end. `graduateStory` (`POST /stories/:id/graduate`, no body) returns the updated `Story` itself (status + `graduatedAt`) — unlike `stagePiece`/`reportBack`, this IS the server-authoritative read, no `getStory` follow-up needed. Picker sources via `listStories` filtered client-side to `REPORTED` **and** `GRADUATED` (broader than the send screen's `DRAFTED`-only filter) — deliberate, so an already-graduated story stays selectable and the decision/confirm UI reappears unconditionally on re-selection (same trick `ReportBackFlow`'s unfiltered send list uses), which is what makes the already-graduated 409 reachable through normal navigation instead of only via a same-request double-click race. Treats the action with weight per the product's human-gated-graduation principle (README §2): the design spec's own decision block ("Ready to take it wider?" / primary "Graduate to wider channels" / secondary "Keep testing — not yet") is layered with an explicit second confirm state ("Graduate this story?" / "Yes, graduate" / "Cancel") before the request fires — clicking the primary CTA arms the confirm, it doesn't submit. Success copy is deliberately honest that graduation is status-only today: no reformat/channel-picker UI built (that's a separate, unbuilt module — the design spec's per-channel "Graduated. This story is heading to X and LinkedIn…" confirmation and channel-toggle state were NOT reproduced, since the backend doesn't trigger reformat). Not-REPORTED 400 and already-graduated 409 (`ConflictException`, "is already GRADUATED") surfaced as specific messages via `describeGraduateError`, reusing `ErrorBanner`'s `message` override. Verified live: full round-trip (REPORTED → confirm → GRADUATED with `graduatedAt` shown) and the already-graduated 409 guard both exercised in-browser, no console errors. Also verified: one full end-to-end walk, single story through all five screens (capture → draft → stage → report-back → graduate) start to GRADUATED, in-browser.
- [x] `/home` (`HomeHub.tsx`, 2026-08-14) — the orchestrating landing screen (the M2 gate): reads `listStories()` and leads with the single most pending action instead of four bookmarks. Priority (heartbeat, not menu): a STAGED story → "How did it land?" → `/report-back?story=<id>`; else a REPORTED story → "Take it wider?" → `/graduate?story=<id>`; else → "What did you ship?" → `/capture` (this branch also covers a genuinely empty pipeline — no separate empty component). Ties within a tier go to whichever story has the most recent `updatedAt`. Below the hero, a compact pipeline list shows every story with a human-readable status badge (`STATUS_LABELS` map — `StatusBadge` just uppercases whatever string it's given, so these labels ARE the badge text). Only STAGED/REPORTED pipeline rows are links (into the same two destinations the hero uses); CAPTURED/DRAFTED/GRADUATED/ARCHIVED rows are plain, non-interactive — `/send` was deliberately left out of the hub's routing entirely (the task brief names only `/capture`, `/report-back?story=`, `/graduate?story=`), so a DRAFTED story's natural next step isn't linked from here despite being a real gap. Capture always stays reachable via a persistent "or capture a new update →" link under the report/graduate hero, so a suggestion never traps the founder into one path. It only ever calls `listStories()` — no `listSends()` — since the hub only needs a Story id for the `?story=` hint; that hint is unread by the existing pickers today, which is fine, the link still lands on the normal picker (verified live). New route mounted at `/home` rather than `/app`, to avoid confusion with the `app/` directory name itself.
  - **Found and fixed a real, app-wide CSS bug while building this**: `globals.css` had a bare `a { color: var(--color-indigo); }` rule sitting outside any `@layer`. Tailwind v4 emits its own utilities inside its `theme/base/components/utilities` layers, and per the CSS cascade-layers spec, *unlayered* rules always beat *layered* ones regardless of specificity — so that rule silently overrode any Tailwind color utility (`text-on-indigo`, `text-muted-2`, ...) applied to an `<a>`/`Link`, not just the default. Nothing had hit this before because no earlier component used `<a>` for a colored button-style CTA (all buttons were `<button onClick>`; `Nav.tsx`'s `#how`/`#pricing` links used `text-text-muted` and were *also* silently broken, just never noticed). Fix: wrapped both rules in `@layer base { ... }` in `globals.css` so normal cascade specificity applies again — confirmed live, `text-on-indigo` now renders correctly (`rgb(247,246,252)` on indigo) on both the hub's CTAs and Nav's links.
  - Verified live: all three hero states (capture/report/graduate) exercised end-to-end against the real backend by walking a story CAPTURED → DRAFTED → STAGED → REPORTED and watching the hero and pipeline badges update correctly at each step; routing into `/report-back?story=` confirmed to land on the real picker; dark mode confirmed fully token-driven (no hard-coded hex); keyboard focus confirmed native (`outlineStyle: auto`) on all of the hub's links, nothing strips it. One console "hydration mismatch" warning observed during testing traced to `data-rm-theme`/`entry-content` attributes and `readermode.io` anchors injected by a Reader-Mode browser extension present in the automated test session — same root cause already flagged in this file's Nav bug entry (2026-08-08), not caused by this change.
  - **Investigation finding (not fixed, out of scope for this task):** neither `CaptureFlow.tsx` nor `SendFlow.tsx` lets the founder edit the generated draft before sending — both render `piece.body`/`drafted.contentPieces[0]?.body` read-only. The backend has no edit capability to hang a UI on either: `ContentPiece` has a single `body` column (no `generatedBody`/`finalBody` split), and `ContentPieceStatus.EDITED` exists in the schema but is unused — its own schema comment says it's there for "an 'edit draft' endpoint, not yet built." So today, if a founder edited a draft before sending, there'd be nowhere for that edit to even go: the M2 send-as-is signal isn't losable yet only because it isn't capturable yet.

## Environment notes

- No global `pnpm` binary on this machine; `corepack enable` and `npm i -g pnpm` both fail on permissions. Use `npx --yes pnpm@latest <cmd>` — works fine, just resolves pnpm on each invocation.
- Registry downloads have been slow/flaky here (pnpm install for `client/web` timed out twice with `ETIMEDOUT`/`ERR_PNPM_UNEXPECTED_STORE` on retry before succeeding on the third attempt with `--network-concurrency 4` and a bumped `fetch-timeout`). If installs hang, that's most likely the network, not a config problem — retry before debugging further.
- `client/web/CLAUDE.md` and `client/mobile/CLAUDE.md` are tool-managed pointer files (`@AGENTS.md`), regenerated by `next dev` / `expo`/create-expo-app respectively — don't hand-edit them or fight their content. This file is the one to keep updated.
- The seeded dev user/audience ids in `client/web/.env.local` (`NEXT_PUBLIC_DEV_USER_ID`) and `api.ts`'s `DEV_AUDIENCES` go stale any time the backend's dev DB gets `TRUNCATE`'d (e.g. running the service's Jest suite, which truncates `User`/`Audience` between tests) — `prisma/scripts/seed-dev-user.js` upserts by fixed email/name, not fixed id, so a fresh id is assigned on the next re-insert. Symptom: every screen 500s (FK violation) even though nothing in `client/` changed. Fix: re-run `node prisma/scripts/seed-dev-user.js` from `service/`, then copy the printed ids into `.env.local` and `DEV_AUDIENCES` by hand. Hit and fixed 2026-08-14.
